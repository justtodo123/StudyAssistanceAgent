## 1. 本文解决什么

以**招聘要求为唯一标准**，重新审视三件事：

1. 现有两份分析（`agent-alignment-analysis.md` + `stage-advancement-analysis.md`）的结论是否成立
2. 本项目距离「能通过 Agent 岗面试」还差什么、差多少
3. 若以招聘标准替代产品路线来排阶段，工作量和风险如何

**核心立场**：本文只回答「能否达标」，不替代产品路线。若两个目标冲突，文中会标注偏离代价。

## 4. 现有分析文档的可行性评估

### 4.1 `agent-alignment-analysis.md` 评估

**核心结论**：「不开新阶段，继续使用与彩排」—— **对产品路线成立，对招聘标准不成立。**

| 其结论 | 招聘标准下的评估 | 判定 |
| --- | --- | --- |
| 「当前更优决策是继续使用与彩排」 | 若目标是通过 Agent 岗面试，**彩排无法弥补 H1/H2 的致命缺口**。面试官会直接问 ReAct 循环和工具注册表，没有实现就讲不出来 | **需要修正** |
| 「不要把 P0 当成现在必须开工的 M6」 | 从产品角度对，从招聘角度错。H1/H2 是 Agent 岗的硬门槛，不是可选项 | **需要修正** |

| 「最小可做范围：Tool 协议 + 可选 ReAct + Agent 评测 + 语义缓存」 | **方向正确，但低估了工作量**（见第 5 节） | 需要细化 |

### 4.2 `stage-advancement-analysis.md` 评估

**核心结论**：「按 M6→M10 顺序推进」—— **依赖链逻辑成立，但节奏太慢，不适合招聘时间线。**

| 「M10 才对接招聘对照的 B1/B2/D1」 | 对产品路线合理，对招聘不合理。H1/H2 是面试核心，不应放在最后一个阶段 | **需重新排期** |

| 阶段顺序：接口→数据源→存储→计划执行→可选 Runner | **逻辑链成立**，但需要在不破坏依赖链的前提下，把 H1/H2 提前 | 可行 |

### 4.3 `StudyAssistanceAgent_requirement.md` 评估

**核心结论**：P0/P1/P2 优先级划分 **基本正确**，但有两个偏差。

| 其判断 | 招聘标准下的评估 |
| --- | --- |
| P0：ReAct + 工具注册表 + Function Calling | **正确**。这是 Agent 岗的核心门槛 |
| P1：语义缓存 + 查询改写 + Agent 评测 + 多模型路由 + 熔断 | **语义缓存应降为 P2，Agent 评测应升为 P0**。评测是证明 Agent 能力的唯一量化手段 |

## 5. 以招聘标准重新排期的方案

### 5.1 设计原则

1. **H1/H2（ReAct + 工具调用）必须尽早落地**——这是面试的致命缺口
2. **不破坏现有依赖链**——Source/Store/Tool 协议仍是基础
3. **保留状态机为默认路径**——教学法不被 LLM 自主决策破坏
4. **每阶段都有可面试讲述的增量**——不留「做完才能讲」的长尾
5. **评估改动工作量**——不复制参考项目的重型架构

### 5.2 建议的新阶段划分

```
M6  → M6a: Harness 骨架（协议先行）+ M6b: Agent 核心（ReAct + 工具调用）
M7  → 用户数据源 + 千级检索（不变）
M8  → 专业化存储（不变）
M9  → 目标驱动计划（不变）
M10 → Agent 评测 + MCP + 多 Agent 了解
```

**关键变化**：将原 M10 的 ReAct + 工具调用**提前到 M6b**，与 M6a 协议先行合并为一个阶段。

### 5.3 各阶段详细分析

#### M6a：Harness 骨架（协议先行）

**与原 `stage-advancement-analysis.md` 的 M6 一致。**

- Source/Store/Tool/Runner 四协议
- 额外 Markdown 源注册
- API 兼容 MVP（`/api/v1/search|qa|quiz|study-sessions` 不变）
- 默认 Runner 仍是学习状态机

**招聘价值**：工具协议是 Function Calling 的基础。面试可讲「我设计了可扩展的工具协议」。

**工作量评估**：中等。主要是接口抽象，不改核心逻辑。预计 2–3 天。

#### M6b：Agent 核心（ReAct + 工具调用）

**原分析将此推到 M10，现提前到 M6b。**

**必须实现**：
1. **工具注册表**：基于 M6a 的 Tool 协议，用装饰器注册工具（`@tool("retrieve", "检索知识库")`）
2. **Function Calling**：LLM 根据工具描述自主选择调用哪个工具
3. **ReAct 循环**：Thought→Action→Observation→Final Answer
4. **安全护栏**：
   - 最大步数限制（建议 8 步）
   - 单步超时（建议 30s）
   - 同一 action+observation 重复 N 次熔断
   - 最终必须落到讲解或复习记录
5. **降级路径**：无 LLM 时 100% 走原状态机

**招聘价值**：★★★★★ 直接补齐 H1/H2 两个致命缺口。面试可讲：
- 「我自研了 ReAct 循环，带最大步数/超时/重复观测熔断三道防御」
- 「工具用注册表+装饰器注册，LLM 自主选择调用」

**工作量评估**：**这是最大的增量工作**。预计 5–8 天。

具体拆解：
- 工具注册表（1–2 天）：定义协议、装饰器、注册机制
- Function Calling（1–2 天）：工具描述序列化、LLM 结构化输出解析
- ReAct 循环（2–3 天）：循环引擎、Observation 注入、Final Answer 提取
- 安全护栏（0.5–1 天）：步数/超时/重复熔断
- 降级路径（0.5 天）：配置开关 + 回退逻辑

**对现有系统的影响**：
- ✅ `study-sessions` API 不变，状态机仍是默认
- ✅ 187 项测试不被破坏
- ✅ 离线 BM25 评测不受影响
- ⚠️ 新增 ReAct 模块，需要新增测试（预计 15–20 项）

#### M7：用户数据源与千级检索

**与原分析一致，不变。**

- 源注册/同步
- FTS5 磁盘全文索引
- 1k–3k chunk 基线测试

**招聘价值**：★★★☆☆ 展示「系统可扩展」的工程能力。

#### M8：专业化存储

**与原分析一致，不变。**

- 统一学习 schema
- 默认 LanceDB
- Qdrant 万级可选

**招聘价值**：★★★☆☆ 展示「存储可替换」的架构设计。

#### M9：目标驱动计划与执行监控

**与原分析一致，不变。**

- 画像（等级/掌握度/目标/每日预算）
- 外部 AI 生成计划
- 按计划选题
- 监控偏差

**招聘价值**：★★★★☆ 展示「Agent 能按目标执行计划」，这是学习 Agent 的产品核心。

#### M10：Agent 评测 + MCP + 对外

**原 M10 的 ReAct 部分已提前到 M6b。M10 专注于评测和协议。**

**必须实现**：
1. **Agent 评测集**：
   - 任务成功率（给一个学习目标，Agent 能否自主完成）
   - 工具调用准确率（是否选对了工具）
   - Token 成本统计
   - 端到端延迟
2. **MCP 协议支持**（建议至少了解 + 最小实现）：
   - 按 MCP 规范暴露工具描述
   - 面试可讲「支持 MCP 协议」
3. **知识包 manifest**：可分发的知识包格式

**招聘价值**：★★★★☆ 评测是证明 Agent 能力的唯一量化手段。MCP 是 2025 后的热门考点。

## 6. 工作量总评估

### 6.1 以招聘标准排期 vs 原 M6–M10 排期

| 维度 | 原 M6–M10 排期 | 招聘驱动排期 | 差异 |
| --- | --- | --- | --- |
| ReAct + 工具调用 | M10（最后） | M6b（第二步） | **提前 4 个阶段** |
| Agent 评测 | M10 | M10 | 不变 |
| MCP 协议 | 不进 M6–M9 | M10 | 从「不做」变为「了解+最小实现」 |
| 多 Agent 协作 | 未规划 | 未规划 | 保持不做（投入产出比低） |
| 语义缓存 | M8 或更后 | M8 或更后 | 不变 |
| 总工期增量 | — | +5–8 天（M6b） | ReAct 是最大增量 |

### 6.2 违反原 PLAN 的影响评估

| 违反项 | 影响 | 风险等级 |
| --- | --- | --- |
| 将 ReAct 提前到 M6b | 需要在协议层（M6a）完成后立即做 ReAct，跳过 M7–M9 的数据和存储准备 | **中**：ReAct 可以先用默认知识包验证，不依赖用户数据源 |
| 不先做用户数据源就做 ReAct | ReAct 调用的工具仍是默认 `knowledge/` 检索 | **低**：面试演示用默认知识包足够，用户数据源是产品需求不是招聘需求 |
| 不先做存储替换就做 ReAct | ReAct 的检索走现有 SQLite 向量 | **低**：向量库选型不影响 ReAct 循环的面试展示 |
| 不先做计划执行就做 ReAct | ReAct 没有「按计划选题」的能力 | **中**：面试时可讲「ReAct 是工具选择层，计划执行是业务层，二者正交」 |

### 6.3 关键结论

**ReAct + 工具调用可以提前到 M6b，且不需要等 M7–M9。**

原因：
1. ReAct 循环只依赖 Tool 协议（M6a），不依赖用户数据源、存储替换或计划执行
2. 面试演示用默认知识包（OS/DS/CO 60 篇）足够
3. 状态机仍为默认路径，ReAct 是可选 Runner，不影响现有功能

### 8.2 M6b 完成后新增可讲

- **ReAct 循环**：「我自研了 ReAct 循环，带最大步数/超时/重复观测熔断三道防御」
- **工具注册表**：「工具用注册表+装饰器注册，LLM 自主选择调用，tool_trace 记录完整轨迹」
- **降级设计**：「ReAct 是可选 Runner，关闭时 100% 走原状态机，无 LLM 时仍可离线运行」

### 8.3 被追问「这算 Agent 吗」的建议答法（更新版）

> 项目有两层：底层是面向学习闭环的领域状态机，编码了教学法（讲解→出题→评估→复习）；
> 上层是可选的 ReAct 推理循环，让 LLM 自主选择工具。
> 两层正交：状态机保证教学法不被破坏，ReAct 保证 Agent 自主性。
> 这不是通用 Agent 框架，而是**领域 Agent 的双层架构**。

### 8.4 M10 完成后新增可讲

- **Agent 评测**：「从 Recall@3 扩展到任务成功率/工具调用准确率/成本/延迟」
- **MCP 协议**：「按 MCP 规范暴露工具描述，支持标准化工具发现」

## 9. 明确不建议做的事（即使招聘 JD 标了）

| 不做项 | 理由 |
| --- | --- |
| 迁移 Java / LangChain4j / Spring | 毁掉 187 项测试和离线交付，面试讲 Python 更友好 |
| 用 Milvus 替换当前向量协议 | 几百 chunk 上 SQLite 已够用，换库不增加面试价值 |
| JWT / 多租户 / Grafana 大盘 | 单用户学习 harness 不是平台运维题 |
| 多 Agent 协作（CrewAI/AutoGen） | 投入产出比低；本项目是单 Agent 学习场景，硬做多 Agent 是过度设计 |
| 模型微调（LoRA/RLHF） | 学习助手不需要微调模型，用好 API 就够 |
| 前端框架重写（React/Vue） | 后端岗不强求，现有工作台够演示 |

## 11. 结论

| 问题 | 回答 |
| --- | --- |
| 现有分析的可行性？ | `agent-alignment-analysis.md` 的「不开新阶段」结论**对招聘标准不成立**；`stage-advancement-analysis.md` 的阶段顺序**逻辑成立但节奏太慢** |

| 建议？ | **先做 M6a（协议）+ M6b（ReAct），再按原顺序做 M7–M10**。这样既不破坏依赖链，又尽早补齐招聘核心缺口 |
