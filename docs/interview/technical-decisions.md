# 技术决策清单

> 本文档记录 StudyAssistanceAgent 项目的核心技术决策，包括选择、放弃、原因和演进条件。
> 用于面试准备，展示工程判断力和 trade-off 分析能力。

---

## 决策 1：知识库存储 — Markdown 文件 vs 数据库

**选择**：Markdown 文件 + Git 版本控制

**放弃**：
- PostgreSQL/MySQL 存储文档
- MongoDB 存储非结构化内容
- 专用知识管理系统（Notion/Confluence）

**原因**：
- **人工维护质量**：个人学习场景下，内容质量比规模更重要，Markdown 便于人工 review 和精炼
- **Git 版本控制**：每次改动可追溯、可回滚、可协作，适合长期维护
- **零依赖**：不需要数据库服务，clone 即用，降低部署门槛
- **可读性**：Markdown 本身可读，不依赖工具即可查看内容

**Trade-off**：
- ❌ 无事务支持，无法保证并发写入一致性
- ❌ 无复杂查询能力（如按时间范围、多条件过滤）
- ❌ 文件系统遍历慢，不适合大规模文档（> 1 万）
- ✅ 简单可靠，适合个人规模和人工维护场景

**何时改变**：
- 知识库 > 1 万文档，文件系统遍历成为瓶颈
- 需要多用户并发编辑，Git 冲突处理困难
- 需要复杂查询（如"最近 7 天更新的 OS 难度进阶的条目"）
- 改为：PostgreSQL 存储元数据 + 全文索引，对象存储（S3）存原始文件

## 决策 2：检索策略 — BM25 + 向量混合检索 vs 单一方法

**选择**：BM25 关键词检索 + 向量语义检索，RRF 融合

**放弃**：
- 纯 BM25（关键词匹配）
- 纯向量检索（语义相似）
- 更复杂的融合方法（学习排序 LTR）

**原因**：
- **互补优势**：BM25 擅长精确关键词（"死锁"、"TCP"），向量擅长语义相似（"进程卡住" → "死锁"）
- **RRF 简单有效**：Reciprocal Rank Fusion 无需训练，效果接近学习排序
- **可选向量**：向量检索需要下载模型（~100MB），设为可选降低入门门槛
- **工程成熟**：两种方法都有成熟的开源实现（SQLite FTS5、sentence-transformers）

**Trade-off**：
- ❌ 两路检索增加延迟（~50ms vs 单路 ~30ms）
- ❌ 向量检索需要额外存储（向量库文件）
- ❌ RRF 参数（k=60）需要调优，但比 LTR 简单
- ✅ 效果优于单一方法，复杂度可控

**何时改变**：
- 需要更精准的排序，引入 LTR（Learning to Rank）
- 检索延迟成为瓶颈，改用近似最近邻（ANN）加速向量检索
- 多语言场景，改用多语言嵌入模型（如 multilingual-e5）

## 决策 3：向量存储 — 可插拔适配器 vs 固定实现

**选择**：VectorStore 协议 + 三种实现（SQLite/Qdrant/Linear）

**放弃**：
- 只用一种向量库（如只用 Qdrant）
- 自己实现向量索引（HNSW/IVF）

**原因**：
- **场景适配**：个人开发用 SQLite（零依赖），生产用 Qdrant（高性能），调试用 Linear（内存）
- **降低门槛**：默认 SQLite 无需额外服务，`pip install` 即可运行
- **扩展友好**：环境变量 `SA_VECTOR_STORE=qdrant` 一键切换，不改业务代码
- **协议抽象**：VectorStore Protocol 定义统一接口，新增实现不影响上层

**Trade-off**：
- ❌ 需要维护多套实现，代码量增加
- ❌ SQLite 向量检索性能有限（~10 万向量以下可用）
- ❌ 不同实现的行为可能有细微差异，需要测试覆盖
- ✅ 灵活性强，适应不同部署场景

**何时改变**：
- 只需要一种实现时，简化为单一向量库
- 需要分布式向量检索时，改用 Milvus/Pinecone
- 向量规模 > 1000 万时，改用专用向量数据库集群

## 决策 4：索引构建 — 全量重建 vs 增量更新

**选择**：全量重建（generation hash 变化时重建整个索引）

**放弃**：
- Chunk-level 增量更新（只 re-encode 变更的 chunks）
- 实时索引（文档变更立即触发更新）

**原因**：
- **简单可靠**：682 chunks 全量重建只需 ~10 秒，代码无 bug 风险
- **不可变性**：每个 generation 的索引是只读的，不会意外污染
- **回滚友好**：旧索引文件保留，可以快速切回
- **规模适配**：个人知识库变更频率低（每周几次），全量重建可接受

**Trade-off**：
- ❌ 浪费计算资源（每次重建都 re-encode 所有 chunks）
- ❌ 重建期间服务不可用（需要额外的切换逻辑）
- ❌ 多版本文件堆积，磁盘浪费
- ✅ 代码简单，无增量更新的复杂性和潜在 bug

**何时改变**：
- 知识库 > 1 万文档，全量重建需要数分钟
- 变更频率高（每天多次），资源浪费不可接受
- 改为：Chunk-level hash 追踪 + Qdrant upsert + 后台异步 worker

## 决策 5：LLM 集成 — 可选降级 vs 必需依赖

**选择**：LLM 可选，未配置时降级为笔记摘要

**放弃**：
- LLM 必需，未配置则服务不可用
- 硬编码默认 LLM（如必须用 OpenAI）

**原因**：
- **开箱可用**：无需 API key 即可运行，降低试用门槛
- **成本可控**：个人项目可以不用 LLM，避免意外账单
- **优雅降级**：笔记摘要仍可学习，只是不如 LLM 生成流畅
- **灵活配置**：支持任何 OpenAI 兼容 API（DeepSeek/OpenAI/本地模型）

**Trade-off**：
- ❌ 降级体验差（笔记摘要是拼接的，不如 LLM 生成连贯）
- ❌ 需要维护两套代码路径（LLM 生成 vs 笔记摘要）
- ❌ 无法保证 LLM 调用失败时的用户体验
- ✅ 适应不同场景（有/无 API key，有/无网络）

**何时改变**：
- 产品化时必须依赖 LLM，移除降级路径
- 需要保证 SLA 时，改用本地部署的 LLM（避免外部依赖）
- 需要多模型切换时，引入 LLM Router（按成本/质量选择模型）

## 决策 6：架构风格 — 单进程 FastAPI vs 微服务

**选择**：单进程 FastAPI，所有功能在一个 Python 进程

**放弃**：
- 微服务架构（检索服务、问答服务、学习服务分离）
- 消息队列（Kafka/RabbitMQ）异步处理
- 多进程部署（Gunicorn + workers）

**原因**：
- **个人规模**：单进程足以处理个人使用的并发量（< 10 QPS）
- **部署简单**：`python tools/start_local.py` 一键启动，无需编排工具
- **调试友好**：单进程易于调试，无需分布式追踪
- **成本低**：无需 Kubernetes、服务网格等基础设施

**Trade-off**：
- ❌ 单点故障，进程挂掉服务不可用
- ❌ 无法水平扩展，单机性能上限
- ❌ 阻塞调用会影响整体响应（如同步 LLM 调用）
- ✅ 简单可靠，适合个人项目和小规模部署

**何时改变**：
- 并发量 > 100 QPS，需要水平扩展
- 需要高可用，引入负载均衡和多副本
- 长耗时任务（如 LLM 调用）阻塞主线程，改用异步队列（Celery/Redis）

## 决策 7：前端技术 — Vanilla JS vs 框架

**选择**：Vanilla JS SPA，无框架依赖

**放弃**：
- React/Vue/Angular 等前端框架
- SSR（服务端渲染）
- 复杂的状态管理（Redux/Vuex）

**原因**：
- **零依赖**：无需 npm install，FastAPI 直接托管静态文件
- **简单直接**：5 个标签页的 SPA，无需框架的复杂性
- **快速加载**：无框架开销，首屏加载 < 100KB
- **维护成本低**：无需跟进框架版本升级

**Trade-off**：
- ❌ 代码组织不如框架清晰（无组件化）
- ❌ 状态管理靠全局变量，复杂场景易出错
- ❌ 无法复用组件，重复代码多
- ✅ 适合小规模前端，维护成本低

**何时改变**：
- 前端逻辑复杂（> 10 个页面，复杂交互）
- 需要组件复用，引入 React/Vue
- 需要 SSR 优化 SEO，改用 Next.js/Nuxt.js

## 决策 8：测试策略 — 阶段隔离 vs 单一测试套件

**选择**：按里程碑阶段隔离测试（M0-M12），每个阶段独立目录

**放弃**：
- 单一 tests/ 目录，所有测试混在一起
- 只写集成测试，不写单元测试
- 只写单元测试，不写集成测试

**原因**：
- **演进清晰**：每个里程碑的测试独立，可以看到项目演进历史
- **回归保护**：tests/regression/ 目录保证旧功能不被破坏
- **快速反馈**：可以只跑当前阶段的测试，无需等待全量测试
- **文档价值**：测试目录结构本身就是项目演进文档

**Trade-off**：
- ❌ 测试文件分散，不易找到某个功能的所有测试
- ❌ 需要维护阶段间的依赖关系
- ❌ 回归套件可能重复覆盖相同功能
- ✅ 适合长周期项目，演进清晰

**何时改变**：
- 项目稳定后，合并为单一测试套件
- 团队扩大，引入 BDD（行为驱动开发）
- 需要更细粒度的测试分类，改用 pytest markers

## 决策 9：数据管道 — 手动维护 vs 自动化 ingestion

**选择**：手动维护 knowledge/ 目录，data/ 目录预留但未启用

**放弃**：
- 自动化爬虫抓取外部资料
- ETL 管道自动转换 PDF/PPT → Markdown
- 用户提交内容自动入库

**原因**：
- **质量优先**：个人学习场景，人工精炼的笔记质量远高于自动化抓取
- **可控性强**：每条内容都经过人工 review，避免低质量内容污染知识库
- **简单可靠**：无需维护爬虫、转换器、审核队列
- **法律合规**：不自动抓取外部内容，避免版权风险

**Trade-off**：
- ❌ 知识库增长慢，依赖人工维护
- ❌ 无法处理大规模外部数据
- ❌ 无法自动更新（如课程大纲变更）
- ✅ 质量高，可控，适合个人学习场景

**何时改变**：
- 需要处理大量外部资料，引入 ETL 管道
- 需要自动更新，引入 CDC（Change Data Capture）
- 需要用户贡献内容，引入审核队列和自动分类

## 决策 10：可观测性 — 结构化日志 + metrics vs 分布式追踪

**选择**：结构化日志（JSON）+ 内存 metrics + 可选 LangSmith

**放弃**：
- 完整的分布式追踪（Jaeger/Zipkin）
- APM 工具（New Relic/Datadog）
- 复杂的告警系统

**原因**：
- **单进程足够**：单进程无需分布式追踪
- **轻量级**：内存 metrics 无需额外存储，重启丢失可接受
- **可选增强**：LangSmith 提供 LLM 调用追踪，按需启用
- **成本低**：无需付费 APM 工具

**Trade-off**：
- ❌ 无法追踪跨请求的完整链路
- ❌ metrics 重启丢失，无法长期分析
- ❌ 无告警，问题发现依赖人工检查
- ✅ 简单轻量，适合个人项目

**何时改变**：
- 微服务架构，引入分布式追踪（OpenTelemetry）
- 需要长期指标分析，引入 Prometheus + Grafana
- 需要告警，引入 PagerDuty/Slack 通知

## 总结：设计哲学

**核心原则**：
1. **简单优先**：在满足需求的前提下，选择最简单的方案
2. **可演进**：关键组件可插拔，预留扩展点
3. **质量 > 规模**：个人项目，内容质量比功能数量更重要
4. **YAGNI**：不为假设的未来需求过度设计

**适用场景**：
- ✅ 个人学习助手
- ✅ 小团队内部工具
- ✅ 原型验证
- ❌ 企业级产品
- ❌ 高并发服务
- ❌ 多租户 SaaS

**演进路径**：
如果项目从"个人学习助手"演进为"企业级产品"，需要改变的优先级：
1. **P0**：索引策略（全量 → 增量）
2. **P0**：向量库（SQLite → Qdrant/Milvus）
3. **P1**：架构（单进程 → 微服务）
4. **P1**：数据管道（手动 → 自动化）
5. **P2**：前端（Vanilla JS → React/Vue）
6. **P2**：可观测性（内存 metrics → Prometheus）

## 面试话术模板

**开场（30秒）**：
> "这是一个个人学习助手，核心是用 RAG 把 Markdown 笔记变成可对话的知识库。目前支持 4 门课程、682 个知识块，实现了完整的问答 → 测验 → 复习闭环。"

**技术亮点（1分钟）**：
> "技术上，我用 BM25 + 向量混合检索，RRF 融合，解决纯关键词无法处理语义相似的问题。向量库和 LLM 都是可选的，未配置时自动降级，保证开箱可用。架构上，关键组件都是可插拔的，比如向量库支持 SQLite/Qdrant 切换，通过环境变量一键配置。"

**设计决策（30秒）**：
> "设计上有几个关键选择：知识库用 Markdown 而不是数据库，因为个人项目需要人工维护质量，Git 版本控制更合适；索引用全量重建而不是增量，因为 682 chunks 重建只需 10 秒，代码简单可靠。这些都是基于当前规模的选择。"

**演进思路（30秒）**：
> "如果扩展到 10 万文档，我会改成 chunk-level 增量索引，用 Qdrant 的 upsert API 更新向量，后台异步处理，实现毫秒级索引更新。如果做成产品，会引入 CDC 监听知识库变更，用 Kafka + Worker 集群处理。当前项目预留了 Qdrant 适配器，切换成本很低。"
