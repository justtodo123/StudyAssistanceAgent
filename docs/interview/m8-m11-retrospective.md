# M8/M11 治理实验复盘

> 本文档记录 M8（专业化存储）和 M11（数据管道）里程碑的治理实验过程，
> 包括为什么构建了复杂的审核系统，为什么最终冻结，以及从中学到的工程判断。

---

## 背景：为什么会有这些工件

2026 年 8-9 月，项目进入 M8/M11 阶段时，尝试构建一套**企业级治理系统**：

- **M8**：专业化存储决策流程（是否引入 Qdrant/Milvus）
- **M11**：外部数据摄入管道（爬虫 → 清洗 → 审核 → 入库）

这两个里程碑都要求**严格的审核流程**：
- 多个独立审核者（reviewer-a, reviewer-b）
- 多轮审核和修订（draft-0.1 到 draft-0.13）
- 严格的授权和冻结机制
- 独立的 worktree 隔离不同审核者的工作

**用途**：每个审核者在独立的 Git worktree 中工作，避免冲突和互相干扰。

**技术细节**：
- 使用 `git worktree add` 创建多个工作目录
- 每个 worktree 有独立的暂存区和工作树
- 通过分支隔离不同审核者的修订

## 治理流程设计

### M8 审核流程

```
1. 提案阶段
   └─ draft-0.1 到 draft-0.5：初步方案设计

2. 审核阶段
   ├─ reviewer-a：独立审核，提出 P0/P1/P2 问题
   └─ reviewer-b：独立审核，提出修改建议

3. 修订阶段
   └─ draft-0.6 到 draft-0.13：根据审核意见修订

4. 授权阶段
   ├─ 每个修订版本需要独立授权
   ├─ 授权记录：m8-v13-authorization-20260910.md
   └─ 处置记录：m8-v13-disposition-20260910.md

5. 冻结阶段
   ├─ 失败链冻结：多次审核未通过，冻结修订
   └─ 执行冻结：未获得执行授权，冻结实施
```

### M11 数据管道流程

```
1. 数据源识别
   └─ docs/reference/document-mapping.json：文档清单

2. 数据获取
   └─ data/raw/：原始数据下载（gitignore）

3. 数据清洗
   └─ data/normalized/：标准化格式（gitignore）

4. 候选审核
   └─ data/candidates/：待审核内容（gitignore）

5. 入库决策
   └─ data/manifests/：元数据清单（git tracked）

6. 拒绝归档
   └─ data/rejected/：被拒绝内容（gitignore）
```

## 为什么冻结

### M8 冻结原因

**直接原因**：
1. **过度设计**：个人项目不需要企业级治理流程
2. **成本过高**：13 轮修订 + 2 个独立审核者 = 大量时间投入
3. **价值不明**：Qdrant/Milvus 对 682 chunks 没有实际收益
4. **机会成本**：花在治理上的时间可以用来改进核心功能

**根本原因**：
- **YAGNI 违反**：为假设的"未来需要"设计了复杂系统
- **规模误判**：用企业级标准要求个人项目
- **目标模糊**：没有明确的"完成"标准，导致无限修订

**决策记录**：
> "现有 SQLite 线性余弦 + BM25 满足当前个人规模，100K 专业化存储容量验证暂缓。"
> — `docs/PLAN.md` M8 状态说明

### M11 冻结原因

**直接原因**：
1. **手动维护更优**：人工精炼的笔记质量远高于自动化抓取
2. **法律风险**：自动抓取外部内容有版权风险
3. **维护成本**：爬虫需要持续维护，应对网站变化
4. **优先级低**：知识库增长不是当前瓶颈

**根本原因**：
- **质量 > 规模**：个人学习场景，内容质量比数量更重要
- **简单可靠**：手动维护虽然慢，但可控且无法律风险
- **YAGNI**：不需要处理大规模外部数据

## 学到的工程判断

### 1. 治理成本必须匹配项目规模

**错误**：为 682 chunks 的知识库设计企业级审核流程

**正确**：
- 个人项目：Git commit + PR review 足够
- 小团队：简单的 CODEOWNERS + 自动化检查
- 企业级：才需要多审核者 + 授权矩阵

**教训**：
> "治理系统的复杂度应该与项目规模和风险成正比。个人项目的过度治理是浪费。"

### 2. 完美是完成的敌人

**错误**：M8 修订 13 轮，追求"完美"的决策文档

**正确**：
- 设定明确的"足够好"标准
- 时间盒限制（如最多 3 轮修订）
- 接受"可逆决策"的不完美

**教训**：
> "可逆决策快速做，不可逆决策慎重做。M8 的存储选择是可逆的（随时可以切换），不需要 13 轮修订。"

### 3. Worktree 隔离策略的价值

**正确做法**：使用 Git worktree 隔离不同审核者的工作

**优点**：
- 避免分支冲突
- 支持并行工作
- 易于对比和合并

**应用场景**：
- 多人协作的大型重构
- 需要对比多个方案的实验
- 需要隔离的审核流程

**保留价值**：这个技术本身有价值，但用在了错误的场景（个人项目不需要这么复杂的隔离）。

### 4. 状态机和审计日志的设计

**正确做法**：每个状态转换都有 JSON 记录和 SHA-256 校验

**优点**：
- 完整的审计追踪
- 支持中断恢复
- 防止篡改

**问题**：
- 过度设计：个人项目不需要这么严格的审计
- 维护成本：状态机逻辑复杂，容易出错

**教训**：
> "审计级别应该与合规要求匹配。个人项目：Git log 足够。金融系统：才需要 SHA-256 校验的状态机。"

### 5. data/ 目录的设计预留

**正确做法**：预留 data/ 目录结构，但大部分内容 gitignore

**优点**：
- 为未来扩展预留空间
- 不影响当前项目
- 清晰的分层（raw → normalized → candidates → approved）

**问题**：
- 预留过度：实际上永远不会用到
- 认知负担：新贡献者会困惑"这些目录为什么是空的"

**教训**：
> "预留扩展点是对的，但不要预留整个系统。如果需要，未来再建。"

## 对面试的价值

### 正面叙事

**展示工程判断力**：
> "项目早期尝试了企业级治理流程，包括多审核者、状态机、worktree 隔离。但后来意识到这是过度设计，冻结了 M8/M11，专注于核心功能。这个决策让我学到：治理成本必须匹配项目规模。"

**展示演进思维**：
> "如果项目从个人工具演进为企业产品，我会重新引入治理，但会更轻量：用 GitHub Actions 自动化检查 + CODEOWNERS 审核，而不是 13 轮人工修订。"

**展示技术深度**：
> "虽然冻结了，但 worktree 隔离和状态机设计本身是有价值的技术。我在其他场景（如大型重构）中会考虑使用。"
