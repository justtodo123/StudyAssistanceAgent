# 问题记录技能

## 描述

在开发和调试过程中，把遇到的非平凡问题标准化记录到 `proced_problem/` 目录，形成一套团队/个人可积累的工程知识库。

## 触发条件

当以下条件同时满足时调用本技能：

1. **问题已经定位到根因并修复完成**（或至少有了明确的根因结论）
2. 问题涉及**至少 2 个排查步骤**——不是一眼能看穿的 trivial error
3. 问题的排查过程有**通用价值**——类似场景下其他人/未来的自己可能再次中招

不应触发的情况：
- 拼写错误、语法错误、lint 告警等 trivial fix
- 一眼能看出的命名冲突/导入路径错误
- 环境的一次性偶发问题（网络超时、磁盘满等）

## 指令

### 步骤 1：确认目录与模板就绪

检查 `proced_problem/` 目录存在，`_template.md` 模板文件存在。若不存在则创建（目录结构见 `proced_problem/README.md`）。

### 步骤 2：分配序号

读取 `proced_problem/` 下的已有 `.md` 文件（排除 `README.md` 和 `_template.md`），取最大序号 +1 作为新记录的序号。

### 步骤 3：按照模板编写记录

以 `_template.md` 为模板，填写以下 7 个章节。要求：

- **症状**：用可观测的语言描述，包含具体数据（如"Recall@3 从 1.000 跌到 0.650"而非"Recall 下降了"）
- **复现条件**：最小复现步骤，最好能写成"只要 X 成立，就能稳定复现"
- **定位过程**：这是最有价值的部分——记下排查链路，包括被推翻的误判（「起初以为 X，后来发现 Y」）
- **根因**：一句话，不要修饰词
- **解决方案**：具体改了什么文件/什么配置，有备选方案的话标注为什么选了这一个
- **验证**：修复前后的数据对比
- **通用经验**：如果未来再遇到类似场景，能提炼出什么原则/检查项

### 步骤 4：更新导航

更新 `proced_problem/README.md` 的记录列表，新增一行在表格末尾。

### 步骤 5：确认

将记录内容展示给用户确认。用户确认后告知文件已保存。

## 行为准则

- 每一节都**必须有具体数据/命令/输出**，禁用模糊描述
- 「定位过程」至少包含 3 个步骤或排除过至少 1 个误判
- 「通用经验」每条都应该是可操作的（可直接塞入 checklist 的句式）
- 模板的 `related_files` 用相对于仓库根目录的路径，`related_pr` 写分支名和 commit hash
