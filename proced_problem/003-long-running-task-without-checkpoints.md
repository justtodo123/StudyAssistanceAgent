# M4 任务范围膨胀且缺少检查点导致长时间无可见成效

## 1. 症状（表现形式）

用户要求在 M3 文件同步后逐步补齐课程知识库，并强调“只做最小完成；耗时过长时可降低验收标准并转为 M4 待办”。实际执行中，核心条目很快生成，但之后长时间没有提交或明确的阶段结果，用户观察到任务执行约 1 小时仍“没有成效”。

可观测时间线：

```text
15:20:16  切换到 feature/m4-knowledge-scale
15:27:07  OS 5 篇、DS 9 篇、CO 10 篇新增条目已创建
15:30:01  DS 最后一篇 dynamic-programming-basics.md 创建
15:53:37  三门课程评测集修改完成
16:33:33  检索排序修复与对应测试完成
16:45:00  M4 计划和项目文档收口
17:14:40  首次提交 106164d
```

从切换分支到首次提交共 1 小时 54 分 24 秒；25 篇核心条目在约 10 分钟内已经完成，但从条目完成到首次提交仍间隔约 1 小时 44 分钟。最终提交涉及 48 个文件、`1620 insertions(+), 103 deletions(-)`，明显超过“知识库规模补齐”的最小范围。

## 2. 复现条件

满足以下条件时容易稳定复现：

1. 用户给出里程碑目标，同时允许耗时任务降级为待办，但没有把“最低交付”和“完整验收”拆成两个明确阶段。
2. 执行者一次性承担条目、导航、评测集、检索质量、测试体系、计划文档和最终回归。
3. 新增知识条目改变 BM25 排名，引发 Recall 回归，执行者继续修改平台代码而未先保存知识库检查点。
4. 受限网络环境仍默认尝试向量检索，Hugging Face 模型不可下载后才切换到 BM25 降级路径。
5. 全量测试和平台测试在开发过程中重复运行，而非只在最终合并前运行一次。

可用以下命令观察“已有大量工作，但 Git 历史仍无进展”的状态：

```powershell
git status --short --branch
git log -1 --date=iso-local --pretty=format:"%h %ad %s"
git reflog --date=iso-local -4
```

当时核心条目已存在，但直到 `17:14:40` 前都没有 M4 提交，工作成果只能表现为大量未跟踪和未提交文件。

## 3. 定位过程

1. **先验证是否真的没有产出**：检查提交 `106164d`，得到 48 个文件、1620 行新增；因此排除“模型一直没有写文件”的误判，问题是产出长期不可见，而不是零产出。
2. **用文件时间定位核心工作完成点**：25 篇新增条目的创建时间集中在 `15:27:07` 至 `15:30:01`，说明内容规模补齐只占前约 10 分钟。
3. **用 Git reflog 定位可见检查点**：分支于 `15:20:16` 切出，首次提交在 `17:14:40`，中间没有按 OS、DS、CO 或“最小完成”拆分提交。
4. **检查后续变更范围**：评测集在 `15:53:37` 修改，`platform/app/retrieval.py` 和 `tests/M4/test_retrieval_priority.py` 在 `16:33:33` 完成，证明任务从知识内容扩展到了检索实现。
5. **核对触发扩展的质量问题**：新增内容后，BM25 降级评测曾出现 DS Recall@3=`0.786`、CO Recall@3 低于 `0.8`；为恢复门槛，又增加候选池扩展、内容类型优先级和测试，最终达到 OS=`1.000`、DS=`0.929`、CO=`1.000`。
6. **量化测试耗时**：M4 定向测试约 13.48 秒；根级 104 项约 146.19 秒；平台 40 项约 145.28 秒。仅一次最终组合验证就耗时约 312 秒，重复运行会持续放大等待时间。
7. **检查环境因素**：默认向量检索在受限环境无法访问 Hugging Face，后续改用 `SA_USE_VECTOR=false`。这不是核心条目生成的阻塞条件，却被纳入同一验收链路。

## 4. 根因

没有在执行开始时把“最小可交付结果”和“完整 M4 验收”分层，也没有设置时间盒和阶段提交检查点，导致检索回归、全量测试与文档收口不断扩大关键路径，已完成的知识条目长期无法形成用户可见结果。

## 5. 解决方案

本次已完成的缓解措施：

- 将 25 篇新增条目、导航、评测集、M4 测试、检索修复和文档统一提交为 `106164d`。
- 课程规模达到 OS/DS/CO 各 20 篇，M4 定向测试 `14 passed`。
- 保留向量不可用时的 BM25 降级验证，不再让 Hugging Face 下载阻塞本地验收。

后续同类任务采用两级验收：

```text
Level 1 最小完成
  按课程补齐条目 -> 更新课程导航 -> 数量/frontmatter 定向测试 -> 阶段提交

Level 2 完整验收
  扩充评测集 -> RAG 指标 -> 必要的检索修复 -> 完整回归 -> 文档收口
```

执行规则：

- Level 1 设 20 至 30 分钟时间盒，按 OS、DS、CO 或可独立审查的批次建立检查点。
- 检索指标不达标但不影响规模目标时，记录为 M4 后续待办，不阻塞 Level 1 提交。
- 开发过程中只跑本阶段定向测试；完整根级与平台测试在准备合并时各运行一次。
- 在受限环境开始评测前显式设置 `SA_USE_VECTOR=false`，避免无效模型下载等待。

## 6. 验证

最终仓库验证结果：

```text
OS 条目数: 20
DS 条目数: 20
CO 条目数: 20
M4 定向测试: 14 passed
根级测试: 104 passed
平台测试: 40 passed
离线 BM25 Recall@3: OS 1.000, DS 0.929, CO 1.000
```

Git 检查点：

```text
106164d feat(knowledge): complete M4 course knowledge scale
48 files changed, 1620 insertions(+), 103 deletions(-)
```

验证表明最终功能和质量门槛已经满足；该问题的修复重点不是重新实现 M4，而是把后续任务的交付路径改为“先形成最小检查点，再处理完整验收”。

## 7. 通用经验

- [ ] 开始任务前写出 Level 1 最小交付和 Level 2 完整验收，禁止两者共用一条无限扩张的关键路径。
- [ ] 对预计超过 20 分钟的任务设置时间盒；到时仍未完成的非核心验收必须转为明确待办。
- [ ] 每完成一个可独立审查的课程或模块，立即建立 Git 检查点，并报告文件数、测试结果和剩余项。
- [ ] 新数据引发质量指标回归时，先判断它是否阻塞当前目标，再决定立即修复还是降级处理。
- [ ] 开发阶段优先运行定向测试；完整回归只在共享逻辑发生变化或准备合并时运行。
- [ ] 受限网络环境中提前关闭需要在线下载的可选能力，显式验证本地降级路径。
- [ ] 状态更新必须体现已完成产物，而不能只报告正在分析、正在测试或仍有未提交变更。
